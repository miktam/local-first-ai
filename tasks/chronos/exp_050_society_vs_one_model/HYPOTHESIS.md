## Question

An estate agency's front desk gets an enquiry and has to answer it: what the sender wants, what to do next, which of the agency's homes to offer, and a reply in the sender's language. That can be built two ways.

- **One model does it all (M).** One call gets the enquiry, the agency's written rules and its whole inventory, and returns the next step, the listings and the reply. This is how most AI tools are built today.
- **A society (G).** Each model answers only what it reads well, and code holds everything between them:

```
enquiry ─► code: language · budget · contacts masked
        ─► Kev-4B + Clef-Flash 9B: closed questions (triage rev 5.1, as live in the bot)
        ─► code: the agency's rules → next step · urgency
        ─► Clef-Flash 9B: closed questions on what the sender needs (area · bedrooms · 8 features)
        ─► code: join with the inventory under the agency's fit rule → up to 3 homes, or none
        ─► gemma4:26b: writes 1–3 sentences in the sender's language, no numbers
        ─► code: listing cards and the closing line rendered from the record (fixed text, 7 languages),
                 then an audit of the model's sentences (language, numbers, contacts)
        ─► READY TO SEND, or NEEDS YOU, with the reason
```

**Measured on the same enquiries, does the society send fewer wrong replies, without handing so much to a person that it stops being useful? And does its decision stay put when the run is repeated and the inventory changes, where one model's may not?**

## Why this experiment

**From The TECH Room (The Pool, 22 October 2026).** A talk there presented an app builder that keeps a fixed core of reusable components, because regenerating everything from scratch makes each new version unpredictable. Our answer is deterministic code that connects the non-deterministic parts. exp_050 tests it on our own front desk instead of asserting it. In G, the listing cards and closing lines are the kernel: fixed, code-rendered text. The model only writes the personal sentences at the edge.

Three more ideas are built into the design:
- **"Where human judgment should remain"** is the junction. G hands a case to a person when the rules say so: spam, a question for the agent, an unsure reading, no home that fits, or a failed audit. The junction is measured both ways: wrong replies that still go out, and good replies held back.
- **If software and intelligence both become cheap, what is left is the agency's own data.** In G, the agency's own material (its inventory and its written rules) enters through code, and the models are parts. H4 tests whether the writer really is a replaceable part: swap the 26B writer for a 4B one and see what moves.
- **Minsky's society of mind.** G has no central controller: no model sees the whole task. The audit is the in-line critic. The **B-brain**, a monitor watching how well each part does, is the calibration report below, the part `the-society-of-mind-impl.md` lists as not yet built. Every NEEDS YOU, with its reason, is a correction a person makes: the record from which the next version learns.

**It brings together the parts tested so far:**

| "we upgraded the question": one bounded question per call, joins in code | exp_012/013, exp_016B/C |

It is also a dated local test of a counter-claim in `deterministic-glue-pipeline.md`, that "the model subsumes the harness" (check date 2028-04). M is that claim: one model in place of the harness.

- **The same writer model in both main arms.** G and M differ in architecture, not in the model that writes.
- **M is told the same routing rule:** set `needs_human` for spam, for a question to the agent, when unsure, and when nothing fits. G applies it in code; M applies it itself.
- **Both arms are told the label date** ("Today is 23 October 2026"). G's timeline question already states it (rev 5.1), and M's prompt states it too (exp_049: timing without a date was the most common error).
- **No Fable arm.** The labels are Fable's and Opus's, so a Fable or Opus arm would partly be marking its own work.
- **Both arms get equal dev effort:** at most three prompt revisions each, recorded. M's thinking mode (on or off) is chosen on dev by wrong replies sent. A tie keeps it off, for time.

## Data (planned)

- **The inventory.** A fictional agency's 60 listings, generated by code (seed 50), with invented refs and plausible, invented prices. They are spread across eight areas: San Pedro, Nueva Andalucía, Guadalmina, Marbella centre, Puerto Banús, Estepona, Benahavís and Elviria. Each listing has an operation (sale or long let only), a type, bedrooms, built m², a price and 8 feature tags (sea view, pool, garden, terrace, parking, walk to the beach, near schools, golf). It is a table with no prose, and both arms get the same table. It stands in for the agency's own data: it is not a real agency's inventory.
- **Labels v4** (`LABELS.md`, written before the writers run): v3, dated Friday 23 October 2026 instead of 21 October, plus:
  - the sender's criteria: areas, type, minimum bedrooms, budget and required features;
  - **the fit rule**, stated once and applied by code to the labels: operation matches intent; type matches if stated (a request for an apartment accepts a penthouse); area matches if stated; price ≤ budget × 1.10; bedrooms ≥ those asked; every required feature present. The agency does no holiday lets, so a holiday enquiry has no fitting home;
  - every contact detail in the message, listed, for H5.
  - **The fitting set of each enquiry is computed by code from its labels and the inventory.** Nobody labels it by hand.
- **Writers:** eight Fable 5.1 writers, the eight languages of exp_049, 45 enquiries each, written against the inventory table. Quotas per writer:
  - 25 standard enquiries (buy, invest, long let), at least one home fits;
  - 6 `no_match`: wants something the inventory doesn't have (area, type, a combination of features, or a holiday let);
  - 5 sellers and valuations;
  - 3 questions for the agent;
  - 6 spam: pitches, scams, other agencies, including some that sound like genuine clients writing through someone.

  Contacts are in Ofcom's drama range and `@example.com` only, checked by the digit-based contact scan and the spelled-out scan before anything is kept.
- **Checker:** Opus 5.5, blind. **A lead is dropped** on any disagreement about intent, next step or a criterion, or on the checker's doubt. That is stricter than exp_049, because the fitting set depends on every criterion.
- **Split** by language × stratum: dev about 80, test the rest (about 240). Andrei reads 30 test leads before signing, as in exp_049.

## What is scored (code, the same for every arm)

**A reply is wrong if any of these holds:**
- **E1:** its next step differs from the label's.
- **E2:** it offers a home outside the fitting set, or offers none when the next step is to send listings and a home fits.
- **E3:** it states a number (a price, size, count, time or reference, in digits or words) that is in neither the enquiry nor an offered listing. **"Grounded" means in the record, not "true".** A correct figure the model knows from its weights counts as ungrounded. That is the agency's rule for anything it sends.
- **E4:** it is not in the sender's language.

**Two outcomes, per enquiry and per run:**
- **Wrong sent:** marked READY and wrong. A reply marked READY to a spam lead is always wrong (E1).
- **Should be ready:** the label's next step is send listings (with a home that fits), ask for details, call now or book a valuation. The other leads should reach a person: spam, questions, and `no_match` with nothing to offer.

## Hypotheses (test set, run 1 unless stated; G against M, paired by enquiry)

| | Measure | Bar |
|---|---|---|
| **H1 safety** | wrong-sent rate over all test enquiries | G ≤ half of M's, and one-sided exact McNemar p < 0.05. If M's rate is under 0.04, G ≤ M |
| **H2 usefulness** | of should-be-ready enquiries, the share READY and right | G ≥ 0.60, and G ≥ M − 0.10 |
| **H3 stability** | the share of enquiries whose decision (READY or not, next step, the set of homes offered) is identical across the 3 runs. The inventory is shuffled for each run, and run 3 adds 2 listings that fit no test enquiry under the fit rule (checked by code) | G ≥ 0.95, and G − M ≥ +0.10 |
| **H4 the writer is a part** | G-small against G: the wrong-sent rate and H2's share | wrong sent rises by at most 0.02; H2's share falls by at most 0.10 |
| **H5 privacy** | labelled contact details (digits normalised; e-mails) in any prompt G sends to any model, all runs. Every prompt is logged to disk | 0 |

Reported, with no bar:
- M+audit, M-small and M-31 against the same measures;
- errors by type (E1–E4), stratum and language; `no_match` separately (does M offer the nearest thing instead of saying there is none?);
- the reasons for NEEDS YOU, counted;
- **the B-brain report:** the calibration of each leaf on test (Kev's and Flash's confidence against accuracy, ECE), and the audit's holds by reason;
- the median time per enquiry and peak memory, per arm;
- **a blind Opus judge** on every READY reply of G and M, run 1. Does it do what its next step says, and does it answer what the sender asked, without asking again for something already given? This catches what the code can't; it decides nothing.

## Verdict map

- **H1 and H2 pass:** the society is the front desk design. It drafts, a person taps send. The next step is a shadow drafter in CasaSol Guide, which is Andrei's call. **H3** gives the measured line about the second version not breaking.
- **H1 passes, H2 fails:** safer, but too much goes to a person. The NEEDS YOU reasons show which junction is too cautious.
- **H1 fails:** on this task, one model is as safe as the society, and the glue hasn't earned its place. Published as such. If M+audit matches G, the code check is what matters, not the decomposition.
- **H4 passes:** a 4B writer can run the desk; the 26B is not needed for this blade. If it fails, the writer is part of the quality, and the post says so.
- **H5 fails:** fix the masker before any real enquiry goes through it.

## What this cannot show

- **Synthetic enquiries** against a **fictional inventory** of 60 homes, written by one family (Fable) and kept only where a second (Opus) agreed. Real inboxes are messier.
- **"Grounded" is the agency's rule, not truth.** E3 counts a correct number from M's memory as an error; on questions for the agent this works against M. Errors are reported with and without the question stratum.
- **The writer's prose is judged only by the reported Opus judge.** The code scores decisions, homes, numbers and language.
- **One prompt design per arm** after at most three revisions on dev. A better M prompt may exist; so may a better G.
- **Same writer model in both main arms:** this isolates the architecture, not the best model. M-31 is the one look at a larger single model.
- **Real enquiries remain the test that matters.**
