# exp_050 incident, 2026-10-23: test pass G r1 aborted after 12 leads

**What happened.** The signed test block started at 10:24 CEST in tmux `exp050-test`. G's run 1 recorded 12 leads:
- 5 "no home fits";
- 1 "a question for the agent";
- 3 spam to review;
- **3 "writer failed: JSONDecodeError"**: every lead that reached the writer.

Dev had 0 writer failures in 90 calls, so at 10:26 the session was stopped and no score was computed. Files: [test_G_r1_20261023-1024.pred.jsonl](test_G_r1_20261023-1024.pred.jsonl) and [test_20261023-1024.log](test_20261023-1024.log). The same files are in casasol `runs/aborted/`.

**Cause: the serving stack, not either desk.**
- **Two gemma runners were loaded.** gemma4:e4b was still loaded from the M-small timing probe on dev; with `OLLAMA_KEEP_ALIVE=-1` it stays loaded. With `OLLAMA_NUM_PARALLEL=2`, its 16K context counts as 32K, a predicted 12.1 GiB. That came on top of gemma4:26b, Kev-4B and Clef-Flash 9B, and free system memory fell to a few GiB.
- **Ollama's log at 10:25:53:** `llama-server terminated ... signal: killed`, then `model predicted to exceed available memory, evicting`, then a reload of gemma4:26b.
- **Around the evictions and reloads,** `/api/chat` returned within about 30 ms an incomplete object (`"done": false`, no `eval_count`, empty content, sometimes an empty model name), or a response cut off mid-thinking. The writer's `json.loads("")` then failed, and the harness recorded that as the model's own failure.
- **Reproduced afterwards on dev prompts:** with only gemma4:26b loaded, the same calls succeeded 6 of 6. Loading e4b next to it brought the incomplete responses back. Switching thinking on or off does not reload the model.

**Decision.**
- The 12-lead pass is archived here and never used. G run 1 starts again from the first lead. No test result was scored or looked at beyond the per-lead log lines above, so nothing in the comparison was chosen after seeing outcomes.
- The design, the bars, the arms and every setting fixed on dev are unchanged.

**Fixes** (casasol, after this incident, before the restart):
1. **One gemma model at a time.** The run script unloads gemma4:e4b before the G and M passes, and gemma4:26b before G-small and M-small.
2. **Serving failures are never recorded as answers** (`desk50.InfraError`). These count as serving failures:
   - an incomplete response (`done` false, no `eval_count`, or a `done_reason` other than stop or length);
   - a dropped connection;
   - Flash missing from the triage. rev 5.1 would fall back to Kev alone, which is not G as defined.

   The runner retries the lead up to 5 times, 60 s apart. If it still fails, the run stops without recording the lead, and a restart resumes there.
3. **A model's own bad output is still the arm's result:** invalid JSON from a call that finished and generated tokens, or a thinking call that hit `length`. That is as defined on dev.
