# Risk Model — Inference Node & Automation Account (miktam02)

*Companion to `HYPOTHESIS.md`, `H3_FINDINGS.md`, and `REMEDIATION.md`. Where those documents record findings and a remediation sequence, this document assesses risk formally — asset, threat, vulnerability, likelihood, impact, treatment, residual risk — and adds a category those documents don't cover: risk generated by the automation's own agentic behavior, not by an external attacker.*

**Date:** 2026-07-12
**Scope:** `miktam-mini` (M4 Pro, automation account `miktam02`) — the machine running local inference, the document-processing pipeline, Hermes, and the Claude Code sessions that administer it.
**Methodology:** Qualitative risk assessment. Risk = f(Likelihood, Impact), each rated Low/Medium/High (Impact adds Critical). Treatment is one of Accept / Mitigate / Transfer / Avoid, per standard risk-management practice. Every entry lists residual risk after treatment — a Mitigate rating does not mean a risk reaches zero.

## Part 3 — Internal / Agentic Risk (not covered by exp_020/021's external threat model)

exp_020 and exp_021 both model an **external or lateral** attacker: something achieving code execution as `miktam02` through a compromised dependency, a misconfigured grant, or a crafted document. Every entry in Part 2 assumes a hostile actor. This part covers a different failure mode entirely: **the automation itself, acting in good faith, doing the wrong thing** — because it hallucinated a fact, misjudged a command's side effects, or was steered by input it trusted. No attacker is required for this category; the "threat actor" is the agent's own fallibility.

exp_021's own `HYPOTHESIS.md` already flagged the adjacent case and explicitly deferred it: *"whether a crafted document fed through the actual pipeline could induce the LLM or its tools to locate and exfiltrate the same secrets H3 checks for directly — prompt-injection-driven exfiltration... a different experiment (candidate: exp_022)."* This section treats that candidate and the pure-hallucination case as one risk family, since the *consequence* and the *missing control* are identical — only the trigger differs (malicious input vs. no input at all, just an error).

### Case study: this session produced the evidence directly

Two real incidents occurred during this session's own remediation work — not hypothetical, not simulated:

1. **`grep -n "TELEGRAM_BOT_TOKEN" ~/.zshrc`** — run to find a line number for a safe deletion. `grep -n` prints the full matching line, including the live token value, directly into the conversation transcript. No malice, no injection — a plain wrong choice of flag.
2. **An automatic file-change-tracking mechanism surfaced a diff of `.zshrc`** after an in-place `sed` edit, and that diff included the live `GOG_KEYRING_PASSWORD` value. This one is more concerning than (1): the agent didn't choose to read anything — a platform-level subsystem surfaced sensitive content as a side effect of a structurally safe edit.

Both are now a standing exposure inside this session's transcript, wherever that is retained.

### Guardrails implemented this session

Two independent controls, deliberately covering different corners of the CIA triad — the same gap in Part 2's threat model (an unattended automation account with broad reach) produces both a confidentiality risk and an integrity/availability risk, and one control does not substitute for the other.

**1. `~/.claude/hooks/block_secret_reveal.py`** (confidentiality) — a `PreToolUse` hook on the `Bash` tool in `~/.claude/settings.json` (global scope — the risk isn't specific to one project). Deterministically blocks any Bash command that both (a) references a known secret-holding path (`.zshrc`, `.zprofile`, `.bash_profile`, `.profile`, any `*.env`, `openclaw.json` and its backups, the `gogcli` keyring tree, SSH private keys, `LaunchAgents`/`LaunchDaemons` plists) and (b) uses a content-revealing form (`cat`/`head`/`tail`/`less`/`more`, `grep` without `-l`/`-c`/`-q`, `sed` without `-i`, inline `python -c`/`node -e` with `print(`/`console.log(`). Safe forms — existence-only `grep`, in-place `sed`, structural JSON rewrites, metadata-only `ls`/`stat` — are explicitly permitted. Fails open on any internal error, so a bug in the guardrail cannot itself become an outage.

Verified live in this session, not just written: pipe-tested against 6 cases (2 should-block, 4 should-allow) before wiring in, then proven against a real Bash tool call — `cat` on a decoy `.env` file was actually blocked mid-session, with the exact denial message shown above in Part 2 (R8).

**2. `dcg` (destructive_command_guard, v0.6.5)** (integrity/availability) — third-party, actively maintained (2.3k stars, 1,761 commits), installed via its own `install.sh --easy-mode --verify`. Same `PreToolUse`/`Bash` interception point as (1), but scans for destructive rather than secret-revealing patterns: `rm -rf` outside safe temp dirs, `git reset --hard`/force-pushes/history rewrites, `DROP TABLE`/`TRUNCATE` across several databases, container/cloud-infrastructure teardown commands. Installer auto-detected and registered hooks not just for Claude Code but also Hermes Agent, Gemini CLI, Codex CLI, and GitHub Copilot CLI on this machine — meaningful because the agentic-risk category in this document isn't specific to one agent runtime. Like (1), it fails open (analysis timeout → allow, not block) so it cannot itself become an outage.

Verified live: `dcg explain "rm -rf ./src"` returned a full BLOCKED rationale with a specific rule ID (`core.filesystem:rm-rf-general`) and suggested safe alternatives; `dcg explain "ls -la /tmp"` correctly allowed a benign command in 1.6ms. Checksum-verified at install; signature verification (sigstore/cosign) did not run — not because it's untrusted, but because the installer's own cosign-version check has a bug against `cosign` 3.1.1 (well above its stated 2.4.0 floor). Logged as a minor residual gap, not treated as a blocker.

### Residual risk — explicitly, not swept under the guardrail

Both controls are **pattern-matching blocklists on one tool (Bash)**, which is a real but bounded mitigation. Together they do **not**:
- Cover the diff-tracking/file-watcher exposure mode (Incident 2) — that subsystem sits outside the documented hook events (`PreToolUse`, `PostToolUse`, `PreCompact`, etc.) and cannot currently be intercepted this way.
- Cover secret-holding paths or destructive-command variants not in each tool's respective pattern set — any new credential file or novel destructive idiom is invisible until added (dcg's maintainers update this continuously across 50+ "packs"; `block_secret_reveal.py`'s list is hand-maintained and narrower).
- Cover exfiltration via `Write`/`Edit` (e.g., copying a value the agent already holds in context into a new file, a commit message, or a chat response) — both controls only see `Bash` commands, not other tools.
- Resolve exp_022 — if a malicious document convinces the agent to construct something other than a matching Bash command (a different tool, a legitimate-looking API call, a subtly reframed request), both controls are silent. exp_022 needs to actually run before that gap can be sized.
- Replace judgment with certainty — both are blocklists, not allowlists; blocklists are inherently incomplete by construction. dcg's own docs concede this directly for one integration: "The [Codex CLI] model can still write scripts to disk to bypass hook-based blocking."

### Recommended next steps (not yet done)

1. Run exp_022 as pre-registered — prompt-injection-driven exfiltration test, the one case this whole session's remediation work has been dancing around without directly measuring.
2. Extend guardrail coverage to `Write`/`Edit` — a basic secret-shape/entropy scan on content being written to a *new* location would catch the "copy a live secret somewhere else" failure mode this session's Incident 1 was one step short of. Neither `block_secret_reveal.py` nor `dcg` currently does this.
3. Consider a semantic second layer (`type: "prompt"` or `type: "agent"` hook, per Claude Code's hook schema) for cases the regex/pattern blocklists can't enumerate in advance — this trades latency/cost for coverage of novel phrasing.
4. Revisit permission mode for `Bash` specifically — this session ran under `acceptEdits`, which is exactly the tool class both incidents came from. A stricter default for `Bash` against known-sensitive-path patterns (ask, not auto-accept) would add a third, independent layer alongside the two new hooks.
5. Re-run `dcg`'s install with `--force` once its cosign-version check is fixed upstream, to get full sigstore signature verification instead of checksum-only.
