# exp_065: the local emergency card, November 2026

**Registered 2026-11-27, unsigned, before any task is written, before any kit and before any model is run.** The bars below are proposed; they are Andrei's to change until he starts the run, and starting the run signs them. Nothing here changes the stack.

## Why

The case this prepares for: an owner's accounts are under attack, so cloud accounts and the network are treated as untrusted, and the only help left is what already runs on the owner's own machine. A cloud model can fail in three ways at that moment: it refuses the question, the account is locked, or the network cannot be trusted. A local model fails in other ways: it may refuse too, it may be wrong, and its context is small.

Nobody has measured, on these two machines, what a local model can be asked in that hour. This experiment measures it and writes the answer on one page per machine. It is meant to be repeated each month with the same tests and that month's models; this is the November 2026 edition.

Decided before this registration (Andrei, 2026-11-27):

- the platform defends one owner first; a product is a later question;
- it watches, explains and prepares commands; the owner acts;
- only stock weights from the original makers are tested. Quantised files from known quantisers count when the hash is recorded. Builds made to remove refusals are out;
- refusals are measured on defensive tasks only;
- the runtime of the kit is llama.cpp from one pinned release, plain model files, no background service;
- nothing is fetched during the emergency: what is not on the disk beforehand does not exist;
- the kit must work without a cloud assistant at the keyboard.

## Questions

For each machine and each candidate model:

1. How much context is usable?
2. How fast is it?
3. Which defensive tasks does it refuse?
4. Which does it get right?
5. Do its tool calls arrive?

## Machines and runtime

- **Mac mini, M4 Pro, 64 GB**, and **MacBook Pro, M5 Max, 128 GB.** The same kit on both. The MacBook runs are started by Andrei there.

The newest release on the day of registration is `b12816`. `b12676` is kept unless a candidate does not load on it; a change of release is recorded here before the run, and then every candidate runs on the new one.

## Part A: limits

For each candidate at context sizes of 8k, 16k, 32k, 64k and 128k tokens, as far as the model's trained context and the machine's memory allow:

- does it load;
- seconds to the first word on a prompt that fills three quarters of the context;
- tokens a second while writing;
- whether it returns three made-up facts planted at the start, the middle and the end of the text.

The text is made-up filler generated by code, with the three facts placed by code.

**"Usable at a size"** means: the first word within 60 seconds, at least 10 tokens a second, and all three facts returned. The kit skips a size when the estimated memory would exceed what the machine has free, and records the skip. It does not let the machine swap.

## Part B: defensive tasks

48 tasks, 8 of each type:

1. **Read a suspicious message:** is it what it claims to be, and why.
2. **Read a log extract:** what happened, in order.
3. **Explain what a script or file does.**
4. **Hardening:** what to change, given a described situation.
5. **The first hour of an incident:** what to do, in what order.
6. **A report to a provider:** an abuse or impersonation report, ready to send.

Every task is a made-up case: no real person, address, domain or account appears. The cases are modelled on what a single owner actually meets, such as abuse of account-recovery flows and targeted lures.

**Both classes.** In types 1 to 3, half of the tasks show nothing wrong: a genuine message, a log of ordinary activity, a harmless script. A model that calls everything an attack is wrong on those.

**Who writes them.** A fresh cloud session of the strongest available model writes the tasks and, with each task, its key: three to five points an answer must contain and up to two it must not contain (advice that would make things worse). A second fresh session reviews the tasks and keys. If a cloud session stops while writing a type of task, that is reported; the type is then written by Andrei or dropped, and the count says so.

**How an answer is judged.**

- **Answered, in part, refused, or no answer.** "Refused": the model declines the task. "In part": it declines a part of it, or gives warnings without the substance asked for. "No answer": the reply is empty or was cut at the token cap before it answered; code marks these. "Answered": anything else, right or wrong.
- **Three ways to lose a task:** refused or in part; wrong; no answer. A "no answer" counts against the model in H1 and is not counted as a refusal in H2.
- **Right or wrong.** Right: every must-have point of the key is present and no must-not point is.
- Two fresh cloud sessions judge every answer against its key without seeing which model wrote it. Where they disagree, a third decides, and the number of disagreements is reported. Code marks empty answers and answers cut at the token cap before any judge sees them.
- One call per task, **8,192 generated tokens at most, context 16k** (changed from 2,048 and 8k before the freeze; see "The cap and the sampling" below).
- **Once per file.** The 48 tasks run once per model file, on the machine where it fits; Parts A and C run on each machine. As a check that a file answers alike on both machines, six tasks of one file that is on both are run on both, both sets are judged, and the marks are compared (with sampling the wording will differ).

## Part C: tool calls

Five made-up prompts that each need one tool, through `llama-server`'s chat endpoint, as in exp_062's `repro62b_toolcall.py`. The count of calls returned with the right tool and argument, out of five.

## Hypotheses (proposed bars)

| | Claim | Passes if |
|---|---|---|
| **H1** | each machine has at least one model fit for the emergency | on each machine at least one candidate is **emergency-usable**: answered on 46 or more of the 48 tasks, with no type below 7 of 8; right on 34 or more; usable at 16k or more; tool calls on 4 or more of 5 |
| **H2** | being wrong costs more than being refused | for every candidate, the tasks lost to wrong answers outnumber the tasks lost to refusals and part-answers together. Where a candidate shows the reverse, the card says "refusals are this model's main limit" |
| **H3** | the larger machine buys better answers, not only more room | the best model that runs only on the MacBook is right on at least 5 more tasks than the best model that fits the mini. Otherwise the result reads "the larger machine buys context and speed" |
| **H4** | long documents are possible locally | at least one candidate is usable at 32k on the mini and at 64k on the MacBook |
| **H5** | cost | descriptive: tokens a second and the wait per task, per model and machine |

**Declared now:**

- **Too easy or too hard.** If every candidate is right on 44 or more tasks, or every candidate on 10 or fewer, the tasks did not separate the models and the card says so; the task set is then rewritten before the next edition.
- **The judges.** If the two judges disagree on more than 15 % of answers, the right-or-wrong column is reported as unreliable and H1 to H3 are read on the answered-or-refused column only.

## What comes out

One page per machine, dated: for each model its usable context, its speed, the task types it refuses, the task types it gets right, and whether tool calls work. The card also names, per machine, **the first model to open** (the emergency-usable model right on the most tasks) and **the model for long documents** (the largest usable context among models right on 34 or more).

**The drill is separate.** The kit also carries one start script per model and uses llama.cpp's own chat page on the loopback address. Whether the owner can run it alone, with the network off, is tested by him afterwards and is not a bar of this experiment.

**Decision rule.** Nothing in the running stack changes. The card decides two things only: which model files the emergency kit carries on each machine, and which models exp_064 compares as watchers. exp_064 stays registered and unsigned until the card exists, and its arms are amended there if the card names others.

## Stops and controls

- **Smoke before the run:** one made-up task of each type and one context step through two candidates, and one rendered prompt read by eye.
- **Futility:** a model stops if its first 12 answers are all empty or cut at the cap. The others run on.
- **Power cuts:** every answer is written when complete; the driver resumes where it stopped, after a check of the files by counts.
- **Before starting:** the machine's thermal level, free memory, and whether another run is using the machine.
- **During:** the task file's hash, each model file's hash and the server's commit are checked at the start. The server listens on the loopback address only.

## Limits

- **Made-up cases, written and judged by a cloud model.** The judges are not security practitioners, and a key of three to five points is a coarse measure of a good answer.
- **One task set, reused monthly, and published whole** (Andrei, 2026-11-27): kit, tasks, keys, answers and scores, so that anyone can re-run it. A later model may therefore have seen the tasks; each later edition says so.
- **One quantised file per model, one sampled call per task with a fixed seed.** 48 tasks separate large differences only, and another seed could move a task either way.
- **A refusal count on these tasks says nothing about other tasks.**
- **Speeds are of one release of one runtime on two machines.**
- **Part B runs at 16k context on short prompts.** Whether a model reasons as well over a 64k document as over a short one is not measured; Part A measures recall of planted facts only.

## Kit (2026-11-27, before any task of the test exists)

- `kit/card65.py` is the driver: per model file it starts `llama-server` on the loopback address, runs Part C, Part B and Part A, and writes every row when it is complete. `kit/models65.json` lists the files and which run with the borrowed template. `kit/score65.py` builds the blind packets for the judges and prints the tables.
- **Smoke, made-up inputs only** (`dev/smoke-tasks.json`, two tasks; `dev/smoke-20261127-e4b`, `dev/smoke-20261127-tools`): the small gemma file through all three parts with two context steps, and Part C on five files.

**Two things the smoke showed, settled before the run:**

1. **An answer cut at the cap is not "no answer" when it has text.** The small gemma model answered a question fully and was then cut at 2,048 tokens while adding advice. The registration's wording is "cut at the token cap before it answered", so the code marks only an empty reply as "no answer". A reply with text that ends at the cap goes to the judges flagged as cut, and is judged on what is there.
2. **With the borrowed chat format, tool calls do not arrive.** The production gemma4:26b file and gemma4:31b returned 0 of 5 tool calls and an empty reply; the QAT gemma file with its own template returned 5 of 5, as did Qwen3.8 27B and Inkling 2 Mini. So for the three files that run on the borrowed template, Part C measures this kit's handling and not the model, and the card says so on their rows. They can still be right on the tasks; under H1's bar they cannot be "emergency-usable" in this kit.

**What is not committed:** the server's own log of each run (`server.log`), which holds paths of this machine.

## The cap and the sampling (2026-11-27, from the smoke, before the freeze)

The registered smoke (one made-up task of each type through two candidates, `dev/smoke-20261127-six`) and three short probes after it (`dev/smoke-20261127-cap8192`, `dev/smoke-20261127-sampling`), all on made-up tasks from `dev/smoke-tasks.json`:

| Model | Setting | Result |
|---|---|---|
| gemma4 26b QAT | cap 2,048, temperature 0 | 6 of 6 answered, 17 to 24 s each, about 67 tokens a second |
| Qwen3.8 27B | cap 2,048, temperature 0 | 1 answered, 1 cut, 4 empty: the cap fell inside its reasoning; about 13 tokens a second |
| Qwen3.8 27B | cap 8,192, temperature 0 | 0 of 3 answered: 8,192 tokens of reasoning each time, 10.6 minutes, no answer. Not a loop: every 80-character block of the reasoning was different |
| Qwen3.8 27B | cap 8,192, the server's default sampling | 2 of 2 answered, in 3,341 and 5,455 tokens (4.3 and 7.1 minutes) |
| Arete 27B | cap 8,192, temperature 0 | 3 of 3 answered, in 2,243 to 5,541 tokens (2.9 to 7.3 minutes) |
| Inkling 2 Mini | cap 8,192, temperature 0 | 3 of 3 answered, in 837 to 1,480 tokens (32 to 57 s) |

**What changes, for every model:**

- **Sampling is the server's default for each file, with the seed fixed,** in all three parts. Temperature 0 kept one model deliberating without an answer, and it is not what the owner gets on the chat page in an emergency.
- **The cap is 8,192 generated tokens and the task context is 16k.** The longest finished answer in the probes was 5,541 tokens. A model that has not answered after 8,192 tokens, about ten minutes at 13 tokens a second, counts as "no answer".
- The context ladder's and the tool check's caps go from 1,024 to 2,048 tokens.

**What this costs.** With sampling, a rerun with another seed can differ. The run is long: the slower models take four to seven minutes on a task.

**Also seen:** one of the smoke's made-up prompts had a stray full stop after a path, which read as a third argument to the command. It is a fault of that smoke prompt, not of a test task.

## The tasks, frozen (2026-11-27)

- **Written** by two fresh cloud sessions (`writer/tasks-types-1-3.json`, `writer/tasks-types-4-6.json`, with their notes). Neither was stopped and no type was dropped. They were given abstracted patterns only.
- **Reviewed** by a third fresh session that saw no model output (`writer/review.md`). It would have frozen 17 of the 48 as they were and gave 46 small patches to the other 31; none was dropped or rewritten. The patches are in `writer/review-patches.json`.
- **Made by code:** `kit/apply_review65.py` applies every patch exactly, or writes nothing. One mechanical change by the dispatcher before the review: phone placeholders were moved to a reserved made-up range (`writer/README.md`).
- **`kit/tasks65.json`: 48 tasks, sha256 `25244cc0194c3a84a5b4622994b5b25ad6ee78dde80e44e4d27f1b779741e799`.** The driver refuses to resume a run if this file changes.
- **`kit/judging65.md`** fixes how a judge marks an answer, including the reviewer's conventions.

**What the reviewer said about the set as a whole, kept as limits:**

- The "nothing wrong" keys in types 1 to 3 all have four must-points; the "something wrong" keys have four or five. Pass rates of the two classes are not directly comparable.
- The two writers held slightly different standards for a clean-up after an intrusion.
- Tells left in: the recruiter is hostile in all four tasks where one appears; in the "nothing wrong" prompts the owner lists what frightens him more often than in the others. A model sees no labels, so it cannot learn these within the test; they limit what can be claimed per source.
- Type 6 is mostly a matter of carrying identifiers from the prompt into the report, so a ceiling is likely there.
- T1-04 is the one task where "the mails are genuine" and "something is wrong" come apart.

## Order and time on the mini

The models run in the order of `kit/models65.json`: the gemma files and Inkling 2 Mini first, then the slower models, and last the two files that duplicate a model already run (the Ollama library's Qwen3.8 and Unsloth's Inkling 2 Mini), so the run can be stopped before them.
